## Claim

Hidden-id permutations produce no change in offered Shapes once *labels* are canonicalised by observable identity. Admission order is PHYSICAL and must NOT be canonicalised away. If hid-sort changes row order (and therefore W), that IS a gauge anomaly.

## How hid was permuted

hid is **not** on the pin_map wire.

hid is GraphElement handle (Record.hid, exclude=True, _elN), off pin_map wire. Operational permutation = shuffled CREATE order (allocator new_hid) plus bijection on optional nickname property id. MATCH/cue use observable slug, never hid/id.

Canonicalisation: node: (kind, payload minus id/hid); edge: (src_obs, rel_type, rel_payload minus id/hid, dst_obs). Emitted sequence is NOT sorted.

Optional nickname property `id` **does** appear on the pin_map wire (see raw example). It is a cue/nickname, not identity; it was stripped before label/order comparison. Internal `Record.hid` (`_elN`) did **not** appear in any pin_map body (`hid_leak_shapes = 0`).

## Mechanism (finding, not a test bug)

`PinMapComposer.compose` seeds with `bounded_match_find` (hits sorted by `r.hid`), then `MemStore.context_pack` → `neighbors` BFS. Incident edges are emitted via `_edge_records`, which **sorts by `r.hid`**. `context_pack` then concatenates nodes then edges and truncates to M in that visit order. `apply_shell_soft_cap` (not used here; default view) also sorts by hid.

So hid is off the agent wire but **on the ranking key**. Shuffling CREATE order (operational hid permutation) changes lexicographic `_elN` order and therefore the offered sequence. That is the gauge anomaly: pin_map leaks hid into order.

M=12 bit on 16-node graphs. The 1-hop set (HUB + 7 DOC + 4 TSK = 12) filled the cap in every original and perm, so **label sets matched**; **sequences did not**. USR (2-hop) never entered W. M was not raised.
